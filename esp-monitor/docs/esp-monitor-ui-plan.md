# ESP Monitor UI 落地方案对比

## 1. 文档目的

这份文档单独说明 `esp-monitor` 的屏幕 UI 应该怎么继续往下做。

当前我们已经验证：

- `ST7789` 屏幕能正常点亮
- 固件能完成基础刷屏
- 指标协议已有明确最小字段集

但目前的显示效果仍然停留在“工程验证版”，主要问题有：

- 自绘 `5x7` 位图字体过于粗糙，成品感很弱
- 当前所有图形都靠手工绘制，迭代 UI 成本高
- 布局调整、字体替换、主题统一都比较费劲

因此后续 UI 演进可以考虑两条路线：

1. 继续使用当前原生绘制方式，但换成更好的位图字体，并重做工业风监控界面
2. 直接切到 `LVGL`，使用成熟 UI 组件、字体和布局系统，一次性把设备侧显示基础打稳

本文就是对这两条路线做专门说明。

---

## 2. 当前约束

在比较方案前，先明确这个项目的设备侧约束。

### 2.1 固件职责边界

`esp-monitor` 只负责：

- 联网
- 请求配置
- 接收标准化指标
- 维护本地状态
- 渲染 UI

它不负责：

- Windows 硬件采集
- 传感器原始字段识别
- 指标标准化规则

### 2.2 当前显示目标

设备侧第一阶段不需要做复杂页面系统，重点是把以下指标显示得稳定、清晰、像成品：

- `cpu.usage_pct`
- `cpu.temp_c`
- `memory.used_mb`
- `memory.total_mb`
- `memory.usage_pct`
- `gpu.usage_pct`
- `gpu.temp_c`
- `network.download_kBps`
- `network.upload_kBps`

### 2.3 当前硬件条件

当前屏幕为：

- `ESP32-C3`
- `240x320`
- `ST7789 SPI TFT`

这意味着：

- 分辨率不算低，但也不适合无节制堆信息
- `SPI` 刷新带宽有限，动画和全屏重绘要克制
- 内存资源有限，UI 框架和字体方案要考虑资源占用

---

## 3. 方案 A：更好的位图字体 + 原生工业风 UI

### 3.1 方案定义

这个方案保留当前技术路线：

- 继续使用 `esp_lcd + spi_master`
- 继续自己控制屏幕绘制
- 不引入完整 GUI 框架

但会做两件关键升级：

1. 把现在简陋的 `5x7` 字体替换成更好的位图字体
2. 重新设计一套工业风监控界面

也就是：

`原生绘制引擎不变 + 字体升级 + UI 重构`

### 3.2 核心思路

在这个方案里，屏幕依然由我们手工绘制：

- 背景
- 分区
- 文本
- 分隔线
- 进度条
- 小图标
- 状态标记

只是把“显示资产”和“布局体系”做得更像成品。

### 3.3 字体部分怎么做

这个方案不是继续手写字符点阵，而是改成正式的位图字体资产。

推荐做法：

- 选择一套适合工业风的小尺寸像素字体
- 导出为 `1-bit` 或 `alpha` 位图字模
- 在固件中加入字体表
- 封装统一文本绘制接口

建议至少准备三档字号：

- 小号：标题、标签、单位、状态文字
- 中号：辅助数值
- 大号：核心指标数字

适合的视觉方向：

- 工业仪表风
- 像素数显风
- 终端监控风

不建议：

- 继续只靠 `5x7` 拼所有文字
- 同时混用太多字号和太多颜色

### 3.4 UI 风格建议

这个方案最适合做成“工业风监控屏”。

建议画面特征：

- 深色背景
- 细分隔线
- 少量高亮色
- 大数字优先
- 小标签辅助
- 弱化装饰，强调信息密度控制

推荐布局：

- 顶部：设备名、连接状态、数据时间
- 中部：`CPU / MEM / GPU` 三个主信息区
- 底部：`NET`、`STALE/OFFLINE`、小状态条

推荐显示节奏：

- 每块只突出一个主值
- 辅助信息控制在 `1~2` 行
- 条形图只做轻量提示，不做复杂动画

### 3.5 这个方案的优点

- 对当前代码改动最小
- 性能可控，资源占用低
- 启动快，绘制链路简单
- 非常适合做“定制感很强”的工业风 UI
- 不需要引入完整 GUI 框架，调试范围小

### 3.6 这个方案的缺点

- 布局、对齐、控件都要自己维护
- 后续做多页面、主题切换会越来越累
- 字体、图标、状态组件都要自己管理
- UI 复杂度一旦上来，维护成本会显著增加

### 3.7 适用场景

这个方案适合下面的目标：

- 先尽快做出一个“好看很多”的可交付版本
- 页面数量不多
- 动画要求很低
- 主要就是一个实时监控主屏
- 项目更强调轻量和可控，而不是 UI 框架能力

### 3.8 预计改造内容

如果选这个方向，建议拆成这些工作：

1. 新增字体资源目录
2. 封装统一字体渲染接口
3. 把当前临时文本渲染替换掉
4. 重做主屏布局
5. 增加状态区
6. 加入离线、重连、无数据三种状态页
7. 再接入 HTTP / WebSocket 实时数据

### 3.9 工作量评估

粗略看，属于“中等工作量”。

原因：

- 不需要改底层驱动栈
- 不需要引入新 UI 框架
- 主要是做字体资产、绘制封装和页面重构

如果页面目标明确，这条路线推进会比较快。

## 4. 方案 B：直接上 LVGL

### 4.1 方案定义

这个方案是把当前“手工画 UI”的模式升级为“框架化 UI”。

核心变化：

- 引入 `LVGL`
- 把屏幕绘制接到 `LVGL display driver`
- 使用 `LVGL` 的字体、标签、容器、进度条、布局能力

也就是：

`ST7789 驱动仍然保留 + UI 层改由 LVGL 管理`

### 4.2 LVGL 是什么

`LVGL` 是一个嵌入式图形界面库，适用于：

- ESP32
- 小屏幕 GUI
- 仪表盘
- 设置页
- 状态页
- 轻量交互界面

它提供的能力包括：

- 文本标签
- 容器布局
- 图表
- 进度条
- 样式系统
- 字体管理
- 动画系统
- 多页面切换

简单说，它能把我们现在要手工做的大量 UI 基础设施直接提供出来。

### 4.3 这条路线怎么接到当前项目

当前底层显示仍可以沿用：

- `esp_lcd`
- `spi_master`
- `ST7789`

需要新增的是：

1. 初始化 `LVGL`
2. 配置显示缓冲区
3. 实现 `flush_cb`
4. 定时调用 `lv_timer_handler`
5. 用 `LVGL` 组件搭页面

数据流仍然是：

`metrics JSON -> 本地状态缓存 -> 更新 UI`

只是“更新 UI”的实现方式从“自己画”变成“修改 LVGL 控件状态”。

### 4.4 这个方案可以带来的变化

一旦接好，很多事情会容易很多：

- 字体可以规范管理
- 文本对齐更容易
- 容器布局更稳定
- 进度条和状态块更成熟
- 多页面结构更容易搭
- 后续设置页、离线页、配网页更容易扩展

这也是为什么很多成熟 ESP32 屏幕项目会直接上 `LVGL`。

### 4.5 这个方案的优点

- UI 基础设施成熟
- 更容易做出“成品感”
- 字体、样式、布局维护成本更低
- 更适合做多状态页面和复杂界面
- 后续演进空间大

### 4.6 这个方案的缺点

- 初始接入成本更高
- 要额外理解 `LVGL` 生命周期和刷新机制
- 需要处理缓冲区和刷屏性能问题
- 对当前项目来说，属于一次中等偏大的架构升级

### 4.7 适用场景

这个方案适合下面的目标：

- 不是只做一个简单监控主屏
- 后续明确还要做状态页、设置页、主题、图表
- 想一次把 UI 架构打好
- 愿意接受前期接入成本换后期迭代效率

### 4.8 预计改造内容

如果选这个方向，建议拆成这些工作：

1. 在 `esp-monitor` 引入 `LVGL`
2. 完成 `ST7789 <-> LVGL` 刷新桥接
3. 建立 UI 初始化和定时刷新机制
4. 做主题、颜色、字体基线
5. 实现在线主屏
6. 实现 `STALE / RECONNECTING / OFFLINE` 状态页
7. 接入 HTTP / WebSocket 数据更新

### 4.9 工作量评估

粗略看，属于“中等偏大工作量”。

原因：

- 要引入新依赖
- 要做框架接线
- 要重写现有 UI 实现

但一旦完成，后续维护体验通常会显著好于纯手工绘制。

## 5. 两个方案的直接对比

### 5.1 技术复杂度

位图字体方案：

- 较低到中等
- 更接近当前实现

LVGL 方案：

- 中等到中高
- 需要额外框架接入

### 5.2 第一版出效果的速度

位图字体方案：

- 更快

LVGL 方案：

- 前期更慢

### 5.3 UI 上限

位图字体方案：

- 中等
- 做一个非常不错的主屏没问题
- 做复杂系统页会越来越吃力

LVGL 方案：

- 更高
- 更适合长期演进

### 5.4 成品感

位图字体方案：

- 取决于字体和设计质量
- 做得好可以很有风格

LVGL 方案：

- 更容易稳定达到“成熟产品界面”的观感

### 5.5 对当前项目的侵入性

位图字体方案：

- 小

LVGL 方案：

- 中等

### 5.6 后续扩展能力

位图字体方案：

- 一般

LVGL 方案：

- 强

## 6. 针对当前项目的推荐

我对当前项目的建议不是简单说“哪个绝对更好”，而是分阶段看。

### 6.1 如果目标是尽快做出一个顺眼的可用版本

优先推荐：

`方案 A：更好的位图字体 + 原生工业风 UI`

原因：

- 当前项目刚完成点屏和基础显示验证
- 现在最痛的问题是“难看”，不是“功能系统太复杂”
- 先把主屏做顺眼，收益最大
- 不会一下子把 UI 技术栈升级得太重

### 6.2 如果目标是后面要持续扩展成完整设备界面

优先推荐：

`方案 B：直接上 LVGL`

原因：

- 后续大概率不止一个在线监控页面
- 还会有离线、重连、配置、主题、图表等需求
- 如果确定会长期演进，早上框架反而更省事

### 6.3 我的实际建议

对当前仓库最稳的推进方式是：

`先做方案 A，把监控主屏拉到可接受的成品感，再评估是否切到 LVGL`

也就是分两阶段：

第一阶段：

- 字体升级
- 做出一版真正顺眼的工业风主屏
- 接上真实指标数据

第二阶段：

- 如果确认要做更多页面和更成熟的 UI 系统
- 再把 UI 层迁移到 `LVGL`

这样做的好处是：

- 风险更低
- 更快出可见成果
- 不会在项目还没稳定时就引入过大的 UI 架构变化

## 7. 推荐的具体落地顺序

如果按我建议的顺序推进，建议这么做。

### 第一步：先升级字体系统

目标：

- 替换当前简陋字符点阵
- 建立统一文字渲染接口

完成后收益：

- 画面质感会立刻提升
- 后续 UI 重构更容易

### 第二步：重做主屏

目标：

- 只做一个在线主屏
- 不急着做太多页面

建议信息层级：

- 顶部：设备名、连接状态、时间
- 主体：`CPU / MEM / GPU`
- 底部：`NET + 状态条`

### 第三步：补状态页

至少做三种：

- `ONLINE`
- `STALE / RECONNECTING`
- `OFFLINE`

### 第四步：接入真实数据

顺序建议：

1. 先接 `GET /api/metrics/latest`
2. 再接 `bootstrap`
3. 最后接 `WebSocket`

### 第五步：再决定要不要迁移到 LVGL

判断标准：

- 是否要多页面
- 是否要复杂布局
- 是否要更规范的 UI 系统

如果这些需求都明确存在，再迁移会更稳。

---

## 8. 两条路线各自的交付物

### 8.1 如果选位图字体方案

最终应产出：

- 一套正式字体资产
- 一套统一文本渲染接口
- 一版工业风在线主屏
- 一组状态页
- 与指标协议对接完成的显示层

### 8.2 如果选 LVGL 方案

最终应产出：

- `LVGL` 接入层
- 显示驱动桥接
- 主题和字体体系
- 在线主屏
- 状态页
- 后续扩展页面骨架

---

## 9. 最终结论

这两个方案并不是互斥的“只能二选一”。

更准确地说：

- `位图字体 + 原生工业风 UI` 更适合当前阶段快速把主屏做漂亮
- `LVGL` 更适合后续把设备侧 UI 架构做成长期可扩展系统

对当前项目，我建议：

先把“位图字体 + 工业风主屏”落地，尽快解决现在屏幕难看的核心问题；
等真实数据接入、状态页需求和页面复杂度都上来后，再决定是否迁移到 `LVGL`。

如果只选一个当前最合适的下一步，那就是：

`先升级字体，不要马上切 LVGL`

因为这一步投入更小，但对观感提升最大，也最符合当前项目阶段。
